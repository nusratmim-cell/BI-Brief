What the brief is asking for

It reads like an analytics dump request. It isn't — the objective line says “for investor diligence”, and every requirement follows from that one reader.

  • A. How much do we know about one learner? A distribution, not company totals. What is actually inside a mature learner's record.
  • B. Does it predict something valuable? Use only the first 7/30/60/90/180 days of behaviour to predict later retention, learning, exam results, purchase and repayment. Report performance, sample sizes and top features.
  • C. How hard is it to recreate? Quantified on breadth, depth, duration, resolution and outcome linkage.
The governing constraint, quoted from the brief

“Do not optimize for the biggest possible number; optimize for numbers we can defend under investor diligence.” Every figure needs a definition, a sample size and an exclusion rule — and measured facts must stay visibly separate from modelled ones.

“For 64,438 learners, Shikho holds 18.9 months of continuous history across 11 signal families, and for 55,020 of them that history is linked to a verified public-exam result.”

The brief says the analysis succeeds if this sentence can be completed credibly. Every figure above is measured. The remaining blank — “…and that history predicts <outcome> with <performance>” — is Deliverable 04 and requires fitting the model.

Query cookbook

Every query below was run against the warehouse on 16 Sep 2026 and its result is shown. The hub key is public."Students".id; almost every learner-scoped table carries it as user_id, except Transactions (student_id) and academic_board_results (joins on reg_no).

Read this first — it decides how you write every query

datafuse.user_activity_daily_logs has no index on user_id (only row_uuid), and academic_board_results has none on reg_no. Any per-learner lookup against them is a full scan of 13.6 M rows. Aggregate the big table once in a CTE and join the small result — never join per learner in a loop. The Metabase API returns HTTP 504 at roughly four minutes, and caps output at 2,000 rows.

Indexes that do exist and are worth using: mcq_user_topic_daily(user_id, date), user_activity_duration_agg(user_id, activity_date, program_id), Students(id), Transactions(student_id), Transactions(tran_date).

Q2Learner-record depth — Deliverables 01, 02, 03~3 min · one full scan
-- The distribution the brief asks for in Question A.
with u as (
  select user_id,
         count(distinct activity_date)                          as active_days,
         sum(activity_count)                                       as events,
         (max(activity_date)::date - min(activity_date)::date)/30.0 as span_months
  from   datafuse.user_activity_daily_logs
  group by 1
)
select count(*)                                            as learners,
       count(*) filter (where span_months >= 3)       as m3,
       count(*) filter (where span_months >= 6)       as m6,
       count(*) filter (where span_months >= 12)      as m12,
       count(*) filter (where span_months >= 24)      as m24,
       count(*) filter (where span_months >= 36)      as m36,
       percentile_cont(0.5) within group (order by span_months) as med_months,
       percentile_cont(0.5) within group (order by active_days) as med_active_days,
       avg(active_days)                                     as mean_active_days,
       max(active_days)                                     as max_active_days
from   u;

-- Swap the outer select for this to get the mature-record anatomy (Deliverable 03):
--   where span_months >= 12  →  64,438 learners, median 18.9 months,
--   67 active days, 318 events, mean 896, p90 2,545

Q3First-N-days features + retention label — the Deliverable 04 base table~4 min · one full scan
-- The brief's core modelling requirement: features from ONLY the first N days,
-- predicting behaviour after day 90. One pass + a window — do not self-join.
with l as (
  select user_id, activity_date, activity_count,
         min(activity_date) over (partition by user_id) as d0
  from   datafuse.user_activity_daily_logs
)
select user_id,
       min(d0)::date                                                            as first_seen,
       count(*) filter (where activity_date <  d0 + interval '7 day')   as active_days_d7,
       count(*) filter (where activity_date <  d0 + interval '30 day')  as active_days_d30,
       sum(activity_count) filter (where activity_date < d0 + interval '7 day')  as events_d7,
       sum(activity_count) filter (where activity_date < d0 + interval '30 day') as events_d30,
       max(activity_count) filter (where activity_date < d0 + interval '30 day') as peak_day_d30,
       -- the label
       (count(*) filter (where activity_date >= d0 + interval '90 day') > 0) as retained_d90
from   l
group by user_id;
Verified — summary over all 994,357 learners
avg active days d7 1.8 · d30 3.1 · avg events d30 17.2
retained past day 90: 159,345 — a 16.0% base rate
Q4Outcome label + class-balance check — run before modelling~5 min
-- Links behaviour to verified SSC board results, and checks whether the

select b.year,
       count(*)                                as linked_learners,
       count(*) filter (where b.is_gpa_5)     as gpa5,
       count(*) filter (where not b.is_gpa_5) as non_gpa5,

Q5Learning minutes per learner — density~4 min
with per_learner as (
  select user_id,
         sum(recorded_videos_duration + animated_videos_duration + live_class_duration
             + quiz_duration + live_exam_duration + model_test_duration
             + smart_notes_duration)/60.0     as minutes,
         count(distinct activity_date)       as active_days
  from   datafuse.user_activity_duration_agg
  group by 1
)
select count(*)                                                    as learners,
       sum(minutes)                                                as total_minutes,
       percentile_cont(0.5) within group (order by minutes)    as median_minutes,
       percentile_cont(0.9) within group (order by minutes)    as p90_minutes,
       percentile_cont(0.5) within group (order by minutes)
         filter (where active_days >= 30)                          as median_minutes_engaged
from   per_learner;

Q6Video abandonment and skips — the brief's hardest video line~30 s on 3,000 rows
-- states is a chunk map: {"chunk_index": true}, chunk_size seconds each.
-- Gaps in the sequence are skips; the highest key is the abandonment point.
-- Raise the LIMIT gradually — the full table is 3.7 M rows.
with w as (
  select id, total_duration, chunk_size, states
  from   public.video_library_aggregated_watch_logs
  where  states is not null and total_duration > 0 and chunk_size > 0
  limit  3000
), k as (
  select w.id, w.total_duration, w.chunk_size, key::int as chunk
  from   w, lateral jsonb_object_keys(w.states::jsonb) as key
), m as (
  select id, total_duration, chunk_size, chunk,
         lag(chunk) over (partition by id order by chunk) as prev
  from   k
)
select id,
       count(*)                                                     as chunks_watched,
       count(*) * max(chunk_size)                                   as seconds_watched,
       least(100, 100.0*(max(chunk)+1)*max(chunk_size)/max(total_duration)) as furthest_pct,
       count(*) filter (where prev is null or chunk <> prev + 1)   as view_runs
from   m group by id;
Verified on a 3,000-record sample
avg chunks watched 120.8 (~20 min) · avg furthest point 55.5% of video
avg separate viewing runs 6.04 · records containing ≥1 skip: 63.0%
Q7Learning loops — failure → remediation → mastery~30 s for a 3-month window
-- Not stored anywhere; constructed. Failure = <50% on a topic that day
-- (min 3 questions); mastery = a LATER day at >=80% on the same topic.
with t as (
  select user_id, topic_id, date,
         sum(total_questions) as q, sum(total_correct) as c
  from   datafuse.mcq_user_topic_daily
  where  date >= date '2026-06-01'          -- widen once you trust it
  group  by 1,2,3
), fail as (
  select user_id, topic_id, min(date) as fail_date
  from   t where q >= 3 and c::numeric/q < 0.5
  group  by 1,2
), recover as (
  select f.user_id, f.topic_id, f.fail_date, min(t.date) as mastery_date
  from   fail f
  join   t on t.user_id = f.user_id and t.topic_id = f.topic_id
         and t.date > f.fail_date and t.q >= 3 and t.c::numeric/t.q >= 0.8
  group  by 1,2,3
)
select (select count(*) from fail)                as failed_episodes,
       (select count(distinct user_id) from fail) as learners_failing,
       (select count(*) from recover)             as recovered,
       (select percentile_cont(0.5) within group (order by mastery_date - fail_date)
          from recover)                            as median_days_to_mastery;
Verified — Jun to Sep 2026
failed episodes 656,518 · learners failing 55,341 · recovered 8,341
recovery rate 1.3% · median days to mastery 6
The window truncates recoveries after Sep — widen the date filter before quoting.

Landmines

Each was hit while measuring the figures on this page. Any one would have put a wrong number in an investor document.

Critical

The outcome label is ~90% GPA-5

The board table is not a representative sample of SSC candidates — it looks seeded for GPA-5 identification. 2022 and 2024 have almost no outcome variance, so a model trained on them is meaningless.

2022 sd 0.037 · 2024 sd 0.073
Usable: 2025 + 2026 only — 55,020 learners, 11,028 non-GPA-5
Critical

Board results are SSC only

academic_type has exactly one value. There is no HSC linkage, so outcome claims must say “SSC” explicitly.

academic_type = ssc_result · years 2022–2026
Critical

Metabase row counts are stale

Wrong by up to three orders of magnitude, in both directions. Never quote the sidebar.

Transactions 2,234 → 247,980
gen_ai_conversations 26,980 → 1,712,867
user_activity_daily_logs 162,950 → 13,559,095
Performance

The biggest tables have no user_id index

Per-learner lookups become full scans and time out at ~4 minutes. Aggregate once in a CTE, then join.

user_activity_daily_logs → only row_uuid
academic_board_results → no reg_no index
video watch logs, gen_ai_* → only id
Empty

Three tables look useful and are not

They have sensible columns and silently return nothing, nulling any metric built on them.

VideoWatchLogs 0 · Topic_Progress 0
program_video_watch_logs 3,245
Design

answer_breakdown has no timestamp

6.41 M answer rows with no date column. Cannot be trended or used in any first-N-days window without joining to a dated parent.

Route via lesson_id / content_id → user_activities.created_at
Scope

Deep tables describe a narrow cohort

The two highest-resolution tables cover a small paid population. Using them for headline breadth overstates by ~40×.

user_activities 14.01 M rows / ~45,000 learners
answer_breakdown 6.41 M rows / 25,487 learners
Windows

Signals start at different dates

A learner record is not uniformly deep. Any completeness claim must state the window per signal.

activity Oct 2020 · AI Jan 2025 · video May 2025
practice MCQ & topic mastery Sep 2025
Gap

No instalment repayment ledger

The brief asks for on-time payment, delinquency and default. Only mandate status exists — there is no due-vs-paid table.

Declare as a gap; do not substitute a proxy.

Handing it back

  • Separate measured from modelled. The brief demands it. Use two visually distinct treatments so a measured fact and a model output never look alike.
  • Every number carries a definition, sample size and exclusion rule. “994,357 learners” means nothing without “≥1 recorded active day, Oct 2020–Sep 2026, excluding test and staff accounts”.
  • Lead with the distribution. Medians and percentiles throughout — the mean is only useful for showing how far the tail drags it.
  • Name the gaps first. Repayment, AI language mix, and the GPA-5 label imbalance. Stating them costs nothing and buys credibility for everything else.
  • Send a memo, not a dashboard. A diligence reader wants a claim they can check, not a tool to operate. Offer the dashboard as backup.
One question worth asking Shahir before starting

Which outcome matters most for the investor conversation? Verified exam results are the most impressive claim but the label is heavily imbalanced and covers 55,020 learners; retention is cleaner, covers 994,357, and is ready to model this week. If time is short, that answer decides where Deliverable 04 goes.
